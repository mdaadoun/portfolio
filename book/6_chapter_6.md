## Introduction: From Textual Data to Exploitable Knowledge

In Chapter 5, you learned how to segment a heterogeneous corpus into coherent text fragments (`chunks`). However, a raw text chunk remains a simple sequence of characters without explicit meaning to a computer. Two sentences might discuss the exact same topic while using entirely different vocabularies; conversely, two sentences might share many words while covering completely unrelated subjects.

The objective of this chapter is to bridge this gap: to transform text into numerical representations that capture *semantic meaning*, to build a search infrastructure capable of querying millions of these representations in milliseconds, and to combine them intelligently to construct a production-grade Retrieval-Augmented Generation (RAG) system.

---

## 6.1 Understanding Embeddings

### 6.1.1 What Is an Embedding?

An **embedding** is a projection of an object (word, sentence, paragraph, image) into a high-dimensional vector space (typically between 384 and 3072 dimensions, depending on the model), where the *geometric proximity* between two vectors reflects their *semantic proximity*.

Concretely, an embedding model (such as OpenAI's `text-embedding-3-large`, Voyage AI's `voyage-3`, or open-source models like `bge-m3`) transforms text:

```
"The cat sleeps on the couch"

```

into a vector of floating-point numbers:

```
[0.0123, -0.0456, 0.0789, ..., 0.0234]  # 1536 dimensions

```

Two semantically similar sentences—even if they share no words in common—will produce vectors that lie close together in this latent space. This property allows a query for `"sleeping feline"` to successfully retrieve a document containing `"The cat sleeps on the couch"`, whereas traditional keyword search would fail.

---

### 6.1.2 Calculating Semantic Similarity

Once text chunks are mapped to vectors, we measure their proximity using vector metrics. Three primary functions dominate the industry:

```
  Cosine Similarity                 Dot Product                     Euclidean Distance (L2)
  (Focuses on Angle)            (Angle + Magnitude)                  (Focuses on Distance)

        d_1                             d_1                                  d_1
       /                               /                                    / |
      / θ                             /                                    /  |
     /____ q                         /____ q                              /___| q
    0                               0                                    0     d(q, d_1)

```

#### Cosine Similarity

Measures the cosine of the angle $\theta$ between two vectors, ignoring their magnitude. It yields a normalized score between -1 and 1 (or 0 to 1 for non-negative vectors). It is widely used in RAG because it remains robust against variations in chunk length.

$$\text{cosine}(\mathbf{q}, \mathbf{d}) = \frac{\mathbf{q} \cdot \mathbf{d}}{\Vert{}\mathbf{q}\Vert{} \Vert{}\mathbf{d}\Vert{}} = \frac{\sum_{i=1}^{n} q_i d_i}{\sqrt{\sum_{i=1}^{n} q_i^2} \sqrt{\sum_{i=1}^{n} d_i^2}}$$

#### Dot Product (Inner Product)

Calculates the sum of point-wise products. It accounts for both angle and magnitude.

$$\text{dot}(\mathbf{q}, \mathbf{d}) = \mathbf{q} \cdot \mathbf{d} = \sum_{i=1}^{n} q_i d_i$$

If vectors are pre-normalized to unit length ($\Vert{}\mathbf{q}\Vert{} = \Vert{}\mathbf{d}\Vert{} = 1$), the Dot Product is mathematically identical to Cosine Similarity. Computing the dot product on pre-normalized vectors eliminates the square root and division operations required for vector magnitudes during query time, significantly accelerating execution.

#### Euclidean Distance ($L_2$ Distance)

Measures the straight-line distance between two points in vector space.

$$d(\mathbf{q}, \mathbf{d}) = \sqrt{\sum_{i=1}^{n} (q_i - d_i)^2}$$

```python
import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def dot_product(a: np.ndarray, b: np.ndarray) -> float:
    return np.dot(a, b)

```

> **Critical Anti-Pattern**: Never mix embeddings generated by two different models (e.g., `text-embedding-ada-002` and `text-embedding-3-small`) in the same vector space. Vector spaces are mutually incompatible between models—a similarity score calculated between vectors from different models is mathematically meaningless. Migrating to a new embedding model requires a full re-indexing of your corpus.

---

### 6.1.3 Selecting an Embedding Model

| Criterion | Impact |
| --- | --- |
| **Dimensionality** | Higher dimensions capture finer semantic nuances but increase memory usage, storage costs, and search latency. |
| **Language Support** | Models trained predominantly on English degrade when processing non-English text. Use multilingual models (`bge-m3`, `text-embedding-3-large`) for multi-language corpora. |
| **Context Window** | Determines the maximum token capacity per chunk (typically 512, 512 to 8192, or 32k tokens). |
| **Cost & Latency** | Commercial API costs scale per token. On-premises or self-hosted open-source models incur compute infrastructure costs instead. |

## 6.2 Vector Databases in Production

Storing millions of vectors in a standard Python list and calculating cosine similarity iteratively works for local prototypes, but fails in production: standard linear search scales at $\mathcal{O}(N \cdot d)$, introducing unacceptable latency as dataset sizes grow.

Vector databases solve this by utilizing **Approximate Nearest Neighbor (ANN)** indexing algorithms. ANN algorithms trade a marginal degree of accuracy (recall) for sub-100 millisecond retrieval speeds over millions of records.

---

### 6.2.1 Indexing Mechanics: HNSW vs. IVF

```
        IVF (Inverted File Index)                   HNSW (Hierarchical Navigable Small World)
┌───────────────────────────────────────┐         Layer 2:  [Node A] -------------------> [Node B]
│ Cluster 1   Cluster 2   Cluster 3     │                   |                             |
│  •  •        •   •       •   •        │         Layer 1:  [Node A] ----> [Node C] ----> [Node B]
│   c1          c2          c3          │                   |            |            |
│  •  •        •   •       •   •        │         Layer 0:  [Node A]-[Node D]-[Node C]-[Node E]-[Node B]
└───────────────────────────────────────┘                   (Dense graph connecting all vectors)
  1. Map query to nearest centroid (c2).
  2. Search ONLY vectors inside Cluster 2.

```

* **IVF (Inverted File Index)**: Partitions the vector space into clusters using k-means. During a query, the engine identifies the closest cluster centroids and searches only the vectors assigned to those clusters.
* **HNSW (Hierarchical Navigable Small World)**: Constructs a multi-layer graph where top layers contain sparse, long-range connections for fast routing, and lower layers contain dense, localized connections. HNSW provides high search speed and recall at the expense of higher RAM usage during index construction.

### 6.2.2 Qdrant

Qdrant is a dedicated vector database written in Rust, designed specifically for production AI systems. It exposes gRPC/REST endpoints and a high-level Python SDK.

```python
from qdrant_client import QdrantClient
from qdrant_client.models import VectorParams, Distance, PointStruct

client = QdrantClient(url="http://localhost:6333")

# Create collection
client.create_collection(
    collection_name="enterprise_knowledge",
    vectors_config=VectorParams(size=1536, distance=Distance.COSINE),
)

# Insert a vectorized chunk
client.upsert(
    collection_name="enterprise_knowledge",
    points=[
        PointStruct(
            id=1,
            vector=embedding_vector,  # List of 1536 floats
            payload={
                "text": "The primary database failover triggers automatically after 30 seconds.",
                "source": "infrastructure_doc.md",
                "tenant_id": "tenant_9941",
            },
        )
    ],
)

# Semantic Query with Metadata Filtering
results = client.search(
    collection_name="enterprise_knowledge",
    query_vector=query_embedding,
    limit=5,
    query_filter={
        "must": [
            {"key": "tenant_id", "match": {"value": "tenant_9941"}}
        ]
    },
)

```

**Payload filtering** allows the system to restrict vector search to specific metadata conditions (e.g., tenant boundaries, permissions, creation dates) during the index traversal phase without degrading query performance.

### 6.2.3 PGVector (PostgreSQL Extension)

`pgvector` adds vector storage and vector search functionality directly to PostgreSQL, allowing teams to keep vector operations within their existing relational database.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE document_chunks (
    id BIGSERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    embedding VECTOR(1536),
    source VARCHAR(255),
    tenant_id VARCHAR(64),
    created_at TIMESTAMPTZ DEFAULT now()
);

-- Build an HNSW index for accelerated search
CREATE INDEX ON document_chunks
USING hnsw (embedding vector_cosine_ops);

-- Similarity query using cosine distance (<=> operator)
SELECT content, source, 1 - (embedding <=> :query_vector) AS similarity
FROM document_chunks
WHERE tenant_id = 'tenant_9941'
ORDER BY embedding <=> :query_vector
LIMIT 5;

```

The `<=>` operator computes cosine distance directly in SQL. This approach allows developers to write relational join conditions across users, permissions, and vector data within single ACID transactions.

---

### 6.2.4 Architecture Selection: Native Vector DB vs. Relational Extension

| Criterion | Dedicated Vector DB (Qdrant) | Relational Extension (PGVector) |
| --- | --- | --- |
| **Large-Scale Performance (>10M Vectors)** | High throughput, optimized memory management | Requires careful resource tuning and hardware allocation |
| **Operational Overhead** | Requires managing a separate infrastructure service | Leverages existing PostgreSQL setup and backup procedures |
| **Relational Integrity** | Non-native; requires synchronization between stores | Native ACID compliance and relational `JOIN` operations |
| **Metadata Filtering** | Built-in payload indexing within vector graphs | Relational `WHERE` filtering prior to or alongside vector operators |

## 6.3 Hybrid Search: Combining Lexical & Semantic Retrieval

### 6.3.1 Limitations of Pure Semantic Search

Dense vector search captures intent and broad semantic context, but can struggle with:

* Exact alphanumeric identifiers, error codes, and SKU numbers (e.g., `ERR_504_BAD_GATEWAY`, `PART-8831`).
* Domain-specific jargon and uncommon acronyms not well represented in the embedding model's training set.
* Rare proper nouns and specific named entities.

To address these edge cases, production retrieval architectures combine dense vector search with sparse keyword search.

---

### 6.3.2 Lexical Retrieval with BM25

**BM25** (*Best Matching 25*) is a term-matching ranking algorithm that scores documents based on query term occurrences. It extends traditional TF-IDF by adding term frequency saturation and document length normalization:

```python
from rank_bm25 import BM25Okapi

corpus_tokenized = [doc.split() for doc in corpus]
bm25 = BM25Okapi(corpus_tokenized)

query = "ERR_504_BAD_GATEWAY database timeout"
scores = bm25.get_scores(query.split())

```

---

### 6.3.3 Fusing Results: Reciprocal Rank Fusion (RRF)

Because sparse search (BM25) returns unbounded floating-point scores while dense search returns bounded similarity metrics (e.g., 0.0 to 1.0), raw scores cannot be directly summed.

**Reciprocal Rank Fusion (RRF)** combines candidate lists by evaluating the relative position (rank) of each document across retrieval systems, bypassing score normalization issues:

$$\text{RRF\_Score}(d \in D) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$

Where:

* $M$ is the set of retrieval systems (e.g., $\{\text{BM25}, \text{Dense Vector}\}$).
* $r_m(d)$ is the 1-based rank of document $d$ in system $m$.
* $k$ is a smoothing constant (standard default is 60).

```python
def reciprocal_rank_fusion(
    vector_results: list[str],
    bm25_results: list[str],
    k: int = 60,
) -> list[str]:
    scores: dict[str, float] = {}

    for rank, doc_id in enumerate(vector_results):
        scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)

    for rank, doc_id in enumerate(bm25_results):
        scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)

    return sorted(scores, key=scores.get, reverse=True)

```

---

### 6.3.4 Second-Stage Filtering: Re-Ranking

Vector similarity calculations use **bi-encoders**, which process query and document vectors independently to enable fast indexed lookups. However, this independent calculation misses fine-grained token-to-token relationships between the query and the text passage.

A **re-ranker** (cross-encoder) processes the query and the text passage simultaneously through a transformer model, evaluating joint token attention across the pair to produce a refined relevance score.

```
User Query: "Fix ERR_502_BAD_GATEWAY in production"
   │
   ├───> Sparse Retrieval (BM25 Keyword Search) ───> Top 50 Docs ──┐
   │                                                               │
   └───> Dense Retrieval (Vector Cosine Search) ───> Top 50 Docs ──┴─> Merged Results (100)
                                                                           │
                                                                           ▼
                                                              [ Reciprocal Rank Fusion ]
                                                                           │
                                                                           ▼
                                                                Top 20 Ranked Candidates
                                                                           │
                                                                           ▼
                                                              [ Cross-Encoder Re-Ranker ]
                                                              (Cohere / FlashRank / BGE)
                                                                           │
                                                                           ▼
                                                                Top 5 Precise Contexts
                                                                           │
                                                                           ▼
                                                                 LLM Prompt Injection

```

Re-ranking strategies include:

* **Cohere Rerank**: Managed API providing cross-encoder models trained for multi-lingual document scoring.
* **FlashRank**: Lightweight local re-ranking library running optimized ONNX cross-encoder models on CPU, avoiding external network overhead.

```python
from flashrank import Ranker, RerankRequest

ranker = Ranker(model_name="ms-marco-MiniLM-L-12-v2")

rerank_request = RerankRequest(
    query="How do I configure the pipeline ingestion timeout?",
    passages=[{"text": doc} for doc in top_k_candidates],
)

reranked_results = ranker.rerank(rerank_request)
final_context = reranked_results[:5]

```

**Two-Stage Funnel Architecture**: Retrieve a broader set of initial candidate chunks (e.g., Top 30–50) using low-cost hybrid search, then pass those candidates through a cross-encoder to select the final chunks (e.g., Top 3–5) for prompt injection.

## 6.4 Mitigating Hallucinations: Strict Grounding

### 6.4.1 Mechanics of Context-Based Hallucinations

RAG pipelines inject retrieved context into the model's prompt to reduce incorrect generation. However, hallucinated responses can still occur due to:

* **Retrieval Gaps**: The retrieval stage fails to surface the necessary context passages.
* **Over-Reliance on Parametric Memory**: The LLM relies on pre-trained internal weights rather than restricting its answer to the provided context blocks.
* **Prompt Ambiguity**: System prompts lack strict boundaries enforcing context isolation.

---

### 6.4.2 System Prompt Design for Grounded RAG

To keep generation grounded, use system prompts that explicitly isolate the model's knowledge space:

```
You are a precise technical assistant. Your task is to answer the user's question 
STRICTLY using the provided context blocks below.

RULES:
1. Rely ONLY on clear facts directly mentioned in the Context. Do NOT use outside 
   knowledge, extrapolate, or make assumptions.
2. If the answer cannot be completely derived from the provided Context, state: 
   "I do not have sufficient information in the provided documentation to answer this question."
3. For every factual claim in your response, append an inline citation referencing 
   the corresponding Source ID, e.g., [Doc-123].

[CONTEXT BLOCKS]
---
Source ID: Doc-881
Content: The primary database failover cluster triggers automatically when node heartbeats fail for more than 30 consecutive seconds.
---
Source ID: Doc-904
Content: Manual failover overrides can be initiated via the internal CLI using `db-admin failover --force`.

[USER QUESTION]
What is the default timeout for automatic database failover, and how do I configure it in the Web UI?

```

---

### 6.4.3 Confidence Scoring & Honesty Filters

In addition to prompt-level constraints, production systems apply programmatic threshold checks before calling the generative LLM. If the top-ranked retrieval or re-ranking score falls below a calibrated relevance threshold, the execution path skips generation and returns a fallback response directly.

```python
CONFIDENCE_THRESHOLD = 0.75

def validate_retrieval_confidence(top_score: float) -> bool:
    return top_score >= CONFIDENCE_THRESHOLD

if not validate_retrieval_confidence(reranked_results[0]["score"]):
    return "I do not have sufficient information in the verified documentation to answer this question."

```

*Note: Relevance thresholds should be calibrated empirically against domain-specific test sets by analyzing score distributions on known true-positive versus false-positive document-query pairs.*
